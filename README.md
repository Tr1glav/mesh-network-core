# mesh-network-core

Ядро mesh-сети на LoRa: радио, кадры, маршрутизация флудом, сообщения, крипто, передача
данных по эфиру (mesh OTA) и настройки узла в NVS. Одно на все прошивки сети — правило
поведения сети, записанное здесь, действует сразу на всех платах.

**Это библиотека, а не прошивка.** Своего `platformio.ini` здесь нет и собрать репозиторий
отдельно нельзя: ядро железозависимо (RadioLib, NVS, `Update`) и компилируется только внутри
прошивки-потребителя.

## Кто его возит

```
Repos/esp32/
├── mesh-network-core/     ← этот репозиторий
├── mesh-network-tools/    проверки на ПК
├── meshcore-fork/         прошивки Heltec (координатор, узел, компаньон, прошивальщик)
└── tdeck/                 прошивка LilyGO T-Deck
```

У прошивок в `platformio.ini`:

```ini
lib_deps =
    symlink://../mesh-network-core
```

`symlink://`, а не копия: по обычному пути PlatformIO один раз копирует библиотеку в
`.pio/libdeps` и дальше её не обновляет, то есть правка ядра локально не видна. Со ссылкой
коммит в ядро мгновенно попадает в обе прошивки — удобно и опасно одновременно, см.
«Версии».

Каталог `lib/meshcore/` внутри каждой прошивки — её **собственный платформенный код**
(экран, плата, признаки сборки), а не копия ядра.

## Что внутри

18 файлов `.cpp` в `src/` плюс встроенная копия ed25519 и 11 заголовков в `include/`.

| Файл | Что в нём |
|---|---|
| `radio.cpp`, `radio_rx.cpp` | RadioLib, профили SF/BW/CR, расчёт времени кадра, приём |
| `mesh.cpp` | опознание узла, кэш публичных ключей соседей, дедупликация кадров |
| `mesh_rx.cpp`, `mesh_tx.cpp` | разбор и сборка кадров, очередь отправки, подтверждения |
| `mesh_channels.cpp` | каналы: ключи, автоключ по имени, открытые каналы |
| `mesh_relay.cpp` | ретрансляция чужих кадров — целиком за `FEATURE_RELAY` (по умолчанию выключена) |
| `ota.cpp`, `ota_slow.cpp`, `ota_receiver.cpp` | mesh OTA: передача данных по эфиру, быстрая и медленная, обе стороны |
| `crypto.cpp` | XOR-поток по HMAC-SHA256, подпись advert (ed25519) |
| `appconfig.cpp` | настройки узла в NVS: имя, WiFi, MQTT, каналы |
| `sensor_tasks.cpp`, `sensor_registry.cpp` | расписание задач узла и реестр сенсоров |
| `button.cpp` | кнопка: антидребезг, короткое и длинное нажатие |
| `strbuf.cpp`, `globals.cpp` | сборка строк без переаллокаций, общее состояние |
| `mc_platform.cpp` | **слабые** заглушки платформенных хуков (см. ниже) |

Заголовки на входе: `mesh.h`, `radio.h`, `ota.h`, `crypto.h`, `appconfig.h`, `config.h`,
`button.h`, `sensor_tasks.h`, `strbuf.h`, `globals.h`, `mc_platform.h`.

## Граница с прошивкой: хуки `mc_platform.h`

В ядре — только то, что одинаково у всех узлов сети. Всё, что зависит от платы (экран,
батарея, WiFi, клавиатура, файловая система, BLE-компаньон), вызывается через функции
`mc*`, объявленные в `include/mc_platform.h`, а прошивка их определяет.

Каждый хук имеет **слабую заглушку** в `src/mc_platform.cpp`. Это сознательный выбор:
прошивка, которой экран не нужен, просто не определяет `mcUiIncoming`, и ядро всё равно
собирается — вместо ошибки компоновки получается тишина. Цена — опечатка в сигнатуре
даёт молчаливое «ничего не происходит» вместо ошибки, и за этим следит отдельная
проверка (`suite_core.weak_hooks_test`): она сверяет сигнатуры заглушек с объявлениями и
с определениями в обеих прошивках.

Признаки сборки (`features.h`, `board_config.h`) живут в прошивке, а **значения по
умолчанию для правил сети — в ядре**: `FEATURE_RELAY` определяется в `include/config.h`
через `#ifndef` и равен `0`. Ретранслятором не должен быть никто по решению владельца
сети; код ретрансляции жив, но включается только явным `-DFEATURE_RELAY=1`.

## Mesh OTA — это передача данных, а не только прошивка

С версии `v0.23.0` mesh OTA — общий протокол доставки N байт с CRC до узла по эфиру. Что
делать с принятым, решает **приёмная сторона** по виду груза (`OTA_KIND_FW_WIRE` /
`OTA_KIND_APP_WIRE`): прошивка уходит в раздел через `Update`, пакет приложения T-Deck —
в хуки `mcOtaDataBegin/Write/Apply/Abort`. Ядро про файловые системы не знает.

Формат образа — `.otaz`: `[OTAZ][размер 4B LE][CRC32 4B LE][zlib]`, описан в `config.h`,
упаковывает `scripts/copy_firmware.py` прошивки.

## Крипто: что он даёт и чего не даёт

Сообщения шифруются XOR-потоком, выведенным из ключа канала, целостность — **первые
2 байта HMAC-SHA256**. Это 16 бит: подделка проходит с вероятностью 1/65536, и тем же
механизмом защищена прошивка, которая едет по радио. Advert подписан ed25519 (встроенная
копия в `src/ed25519/`), но от переигрывания не защищён, IV/nonce в сообщениях нет.

Это известные ограничения протокола, а не недосмотр: любая правка здесь ломает
совместимость со всеми узлами в эфире, поэтому они меняются **одним выпуском и с
миграцией** (ширина MAC, IV, защита advert от переигрывания, advert ACK, фрагментация).
Задача на доске проекта.

## Проверки

Проверки ядра живут в соседнем репозитории `mesh-network-tools` — одним набором на все
прошивки, потому что ядро у них одно:

```
cd ../mesh-network-tools && python3 selftest.py --target core
```

Железо не нужно: проверки вырезают из этих исходников настоящие функции (CRC, `floodGapMs`,
`buildPingReply`, `rawBuildFrame`, `maybeQueueRelay`), собирают их хостовым `g++` с
`-fsanitize=address,undefined` и гоняют на граничных данных. Набор `suite_core.py` идёт для
**любой** цели — правка ядра проверяется и при сборке каждой прошивки.

**Каждая правка ядра обязана получить проверку, падающую на откате.** Если после отката
правки проверка всё ещё зелёная — она ничего не проверяет.

## CI

`.github/workflows/checks.yml`, два задания:

- `core` — проверки ядра в одиночку (цель `core`: ни одной прошивки рядом нет);
- `consumers` — сборка **обоих потребителей против этого коммита ядра**, а не против их
  пина. Иначе выпуск ядра ломает прошивку уже после тега: так и вышло, когда расписание
  задач узла переехало в ядро — T-Deck собрался локально (ссылка на рабочее дерево) и упал
  в своём CI (там ядро берётся по `core.ref`). Приватный `tdeck` выкачивается deploy key'ем
  только на чтение; нет ключа — ветка матрицы пропускается с записью в журнал, а не краснеет.

## Версии

Версия объявлена в двух местах, и оба обязательны: тег git (`v0.23.0`) и `"version"` в
`library.json` — его PlatformIO печатает в журнал сборки. Прошивки пинятся на тег своим
файлом `core.ref`; расхождение сверяет `suite_core.core_version_test`.

**Минорный номер** ставится, когда правка меняет состав библиотеки так, что прошивки больше
не соберутся с предыдущим тегом, — даже если поведение сети не изменилось. Патч-номер — для
правок, после которых прошивка собирается со старым и с новым ядром одинаково. Смысл в том,
что `core.ref` — это пин для CI: минорный номер прямо говорит, что переход через него
требует правки `core.ref`, а не «подтянется само».

Порядок выпуска: тег ядра → `core.ref` обеих прошивок → отправка прошивок. Режим поломки
(локально собирается, CI прошивки падает) закрыт с двух концов: `release.py` прошивки
отказывается отправлять при расхождении, а задание `consumers` собирает потребителей до
тега.

Зависимость RadioLib пинится **коммитом**, а не версией: `library.json`.
